# 需求文档

## 1. 背景
- 业务背景：数据调度页面“操作 -> 查看日志 -> 数据提取日志”需要接入真实数据源。
- 当前现状：日志接口仍为占位逻辑，调用后无法返回真实日志记录。
- 相关页面/模块：
  - `frontend/src/pages/(base)/data-fetch/data-schedule/index.tsx`
  - `frontend/src/pages/(base)/data-fetch/data-schedule/modules/ScheduleLogModal.tsx`
  - `backend/api/views.py`

## 2. 目标
- 核心目标：日志接口按 `projectId` 查询 `c_r_cm_task_item_queue` 并返回前端可展示数据。
- 预期价值：日志查看功能可用，便于排查任务执行问题。

## 3. 范围
### 本次范围
- 支持日志接口通过 `projectId` 查询队列表数据（只读）。
- 返回数据映射到日志表格字段（time/component/level/message）。
- 前端透传 `projectId` 到日志接口。

### 不在本次范围
- 队列表写入、修数、DDL。
- 改造日志弹窗 UI 结构。

## 4. 用户故事
- 作为 `数据调度使用者`，我希望 `按项目查看数据提取日志`，从而 `快速确认任务执行状态与异常原因`。

## 5. 功能需求
- [x] 需求 1：`logs/meta`、`logs`、`logs/export` 接口支持 `projectId` 查询参数。
- [x] 需求 2：接口数据源改为 `c_r_cm_task_item_queue`（只读查询）。
- [x] 需求 3：前端“查看日志”请求携带当前行 `projectId`。
- [x] 需求 4：无日志数据时返回空列表，不抛前端不可处理错误。

## 6. 非功能需求
- 性能：单项目日志查询在常规数据量下可快速返回。
- 安全性：仅执行 `SELECT`，不执行写库 SQL。
- 兼容性：保留原 `task_id` 路径，避免影响既有调用方。
- 可维护性：通过 helper 封装项目日志查询与映射逻辑。

## 7. 数据与接口影响
- 前端影响：日志相关类型、hooks、api 请求参数新增 `projectId`。
- 后端影响：日志相关 view 从占位逻辑切换为真实查询逻辑。
- 数据库影响：仅查询 `c_r_cm_task_item_queue`，无写操作。
- 第三方/MCP 影响：无。

## 8. 交互与界面说明
- 日志弹窗交互保持不变。
- 需要覆盖状态：加载中 / 空态 / 成功 / 查询异常。

## 9. 验收标准
- [ ] 从数据调度列表点击“查看日志”可看到真实日志数据。
- [ ] 请求包含 `projectId`，后端按项目查询日志。
- [ ] 日志筛选、排序、导出流程可用。
- [ ] 无数据时显示空态，不报错。

## 10. 风险与疑问
- 风险：不同环境队列表字段可能存在差异，需要兼容缺失列。
- 疑问：无。

## 11. 确认关卡
- 用户已明确确认本需求进入编码实现阶段。
