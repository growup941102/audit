# 需求文档

## 1. 背景
- 业务背景：数据调度详情页已有“编辑”操作和弹窗，但真实数据链路下“编辑”按钮不可用，且编辑后未真正落库。
- 当前现状：
  - 后端真实字段组装时将 `canEdit` 固定为 `false`，前端按钮被禁用；
  - 字段更新接口当前只写入进程内存 `DATA_SCHEDULE_FIELD_OVERRIDE_STORE`，不会写入 MySQL；
  - 页面刷新或服务重启后，编辑结果无法持久保留。
- 相关页面/模块：
  - 前端：`frontend/src/pages/(base)/data-fetch/data-schedule/modules/ScheduleDetailView.tsx`
  - 后端：`backend/api/views.py`（字段列表与字段更新接口）

## 2. 目标
- 核心目标：
  - 数据详情列表中的“编辑”操作可点击；
  - 点击编辑弹窗保存后，字段内容可写入数据库并可再次查询到。
- 预期价值：
  - 让数据调度详情具备真实可维护能力，支持纠偏与二次核验；
  - 避免“前端看似修改成功但实际未持久化”的认知偏差。

## 3. 范围
### 本次范围
- 开启真实详情字段的可编辑能力（仅允许安全字段）。
- 打通字段编辑接口到数据库 `UPDATE`。
- 保持现有前端交互（编辑弹窗、保存后刷新）不变。

### 不在本次范围
- 不新增数据库表或迁移。
- 不改下钻弹窗行编辑能力（本期聚焦主列表“字段编辑”）。
- 不引入新的权限系统（沿用当前登录态鉴权）。

## 4. 用户故事
- 作为 `数据调度使用者`，我希望 `在数据详情中点击编辑并保存字段值`，从而 `确保修正内容真实入库并可追溯`。

## 5. 功能需求
- [ ] 需求 1：字段列表返回的可编辑字段 `canEdit=true`，前端“编辑”按钮可点击。
- [ ] 需求 2：点击“编辑”打开弹窗，保存后调用现有 PATCH 接口成功返回。
- [ ] 需求 3：PATCH 成功后对应业务表字段已更新（非内存态）。
- [ ] 需求 4：页面刷新后，字段展示仍为更新后的值。
- [ ] 需求 5：不允许编辑受保护字段（如主键/关联键/系统字段），接口需给出明确错误提示。

## 6. 非功能需求
- 性能：单次字段更新接口在常规场景应保持低延迟（仅单行更新）。
- 安全性：
  - 仅允许更新已识别的真实表与列；
  - 严格参数校验，避免 SQL 注入风险。
- 兼容性：不改变前端现有 API 调用方式与响应结构。
- 可维护性：字段可编辑判定与数据库更新逻辑独立封装，便于后续扩展。

## 7. 数据与接口影响
- 前端影响：无新增接口，复用现有 `updateDataScheduleExtractField`。
- 后端影响：
  - 调整字段列表组装逻辑（返回可编辑标识）；
  - 调整字段更新逻辑（由内存写入改为数据库写入）。
- 数据库影响：
  - 对数据调度详情来源表执行单字段更新；
  - 不涉及表结构变更。
- 第三方/MCP 影响：无。

## 8. 交互与界面说明
- 主表“操作”列：可编辑字段显示可点击“编辑”，不可编辑字段保持禁用。
- 编辑弹窗：沿用当前文本输入与保存按钮交互。
- 保存反馈：成功提示 + 列表刷新；失败提示原因。

## 9. 验收标准
- [ ] 数据详情页至少存在一条可编辑字段，点击“编辑”可打开弹窗。
- [ ] 保存后接口返回成功，页面列表显示新值。
- [ ] 直接查询数据库，目标表目标字段值已变化。
- [ ] 刷新页面后新值仍然存在。
- [ ] 尝试编辑受保护字段时，接口返回 4xx 且提示“当前字段不支持编辑”或等价错误。

## 10. 风险与疑问
- 风险：
  - 现有字段 `fieldKey` 包含行序号，若缺少稳定行标识，可能带来定位歧义；
  - 不同详情表字段类型差异大，字符串写入需做兼容处理。
- 疑问：
  - 可编辑字段白名单是否需要进一步收敛到“业务字段清单”（而非规则推断）。
