# 需求文档

## 1. 背景
- 业务背景：数据调度任务执行过程中会产生阶段性日志，当前页面仅有“执行日志”入口，缺少可查看、筛选、排序、导出的完整能力。
- 当前现状：`data-schedule` 列表“更多”菜单已有“执行日志”文案，但无实际日志界面与接口联动。
- 相关页面/模块：
  - `frontend/src/pages/(base)/data-fetch/data-schedule/index.tsx`
  - 参考图：`/Users/zyc/gxxm/audit/demand/log.png`

## 2. 目标
- 核心目标：实现“数据调度日志”弹窗页面，并接入后端日志查询与导出接口。
- 预期价值：
  - 支持执行过程可观测；
  - 支持按日志级别与时间顺序快速定位问题；
  - 支持日志文件导出，便于审计与离线归档。

## 3. 范围
### 本次范围
- 在数据调度列表页点击“执行日志”后打开日志弹窗。
- 弹窗展示任务日志基础信息（项目名称、服务名称、执行节点）。
- 日志表支持：
  - 日志级别筛选：`info`、`warn`、`error`
  - 时间排序（升序/降序）
  - 关键字搜索（日志内容）
  - 时间范围筛选（开始日期/结束日期）
  - 按条数查询日志（默认最近 `100` 条）
- 支持导出当前筛选条件下的日志。
- 界面风格参考 `demand/log.png`。

### 不在本次范围
- 日志实时 WebSocket 推送。
- 日志编辑/删除。
- 跨任务聚合日志。

## 4. 用户故事
- 作为 `调度任务查看者`，我希望 `在任务列表中查看任务执行日志并按条件筛选与导出`，从而 `快速定位异常并完成留档`。

## 5. 功能需求
- [ ] 需求 1：点击“执行日志”打开日志弹窗，默认加载最近 100 条日志。
- [ ] 需求 2：日志级别支持 `info/warn/error` 三档筛选。
- [ ] 需求 3：日志时间支持升序/降序排序切换。
- [ ] 需求 4：支持按关键字、时间范围查询日志。
- [ ] 需求 5：支持“刷新”动作重新拉取日志列表。
- [ ] 需求 6：支持“导出”当前筛选结果。
- [ ] 需求 7：支持按条数查询（`count`），并限制上限防止超大查询。

## 6. 非功能需求
- 性能：常规查询接口在 2 秒内返回（不含超大数据场景）。
- 安全性：接口继承现有鉴权机制（登录态 + Token）。
- 兼容性：保持与当前前端请求封装、后端响应结构一致。
- 可维护性：前端拆分为弹窗组件 + service/hooks/types，后端按 views + urls 明确职责。

## 7. 数据与接口影响
- 前端影响：
  - 新增日志弹窗组件与 hooks/service/types；
  - 列表页“执行日志”菜单绑定弹窗打开逻辑。
- 后端影响：
  - 新增日志元信息接口；
  - 新增日志列表接口（筛选+排序+按条数）；
  - 新增日志导出接口。
- 数据库影响：本期优先可替换数据源（mock/临时数据），不强制新增表。
- 第三方/MCP 影响：无新增 MCP 依赖。

## 8. 交互与界面说明
- 参考图：`demand/log.png`
- 关键交互：
  - 顶部：任务信息 + 刷新 + 导出；
  - 中部：搜索、级别筛选、日期范围、排序开关；
  - 底部：日志表（时间/组件/等级/日志）。
- 可抽离的组件机会：
  - `ScheduleLogModal`（弹窗容器）
  - `ScheduleLogFilters`（筛选条）
  - `ScheduleLogTable`（日志表格）
- 需要覆盖的状态：加载中 / 空态 / 异常 / 成功。

## 9. 验收标准
- [ ] 点击“执行日志”可打开弹窗并看到日志数据。
- [ ] 默认查询参数为“最近 100 条”，且首屏展示符合该条件。
- [ ] 级别筛选仅支持 `info/warn/error`，且筛选结果正确。
- [ ] 时间排序可切换升序/降序，列表顺序与参数一致。
- [ ] 导出文件可下载，且内容与当前筛选条件一致。
- [ ] 关闭弹窗后再次打开，保持可预期的默认查询状态。

## 10. 风险与疑问
- 风险：
  - 日志数据量大时，导出耗时与接口超时风险上升。
  - 如果后续切换真实日志源，字段规范可能变化。
- 疑问：
  - “按条数查询”的最大上限暂定为 `1000`，若需更大范围再调整。
