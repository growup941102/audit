# Audit Integration Fast Loop

用于 `/Users/zyc/gxxm/audit` 项目联调修复阶段的高效沟通流程。  
本 skill 关注“沟通与闭环节奏”，不替代具体业务排查能力。

## 1. 适用场景
- 同时存在多个联调问题，需要并行推进且避免信息遗漏。
- 用户强调“沟通更高效”“少来回确认”“快速看到阻塞与结论”。
- 修复过程频繁涉及前后端契约核对、日志排查、状态同步。

## 2. 启动规则（开场 1 次）
开始联调时先给出一条“联调启动卡”，包含：
- 目标范围：本轮联调覆盖哪些模块/接口。
- 问题池：当前问题数量与优先级（P0/P1/P2）。
- 协作节奏：默认每 15-20 分钟同步一次短进展。
- 决策门禁：哪些动作会停下等待用户确认。

## 3. 问题卡模板（每个问题一张）
每个问题统一按以下结构同步：
- `问题ID`：
- `现象`：用户可见结果与实际偏差。
- `复现条件`：环境、参数、步骤。
- `当前定位`：已确认事实，不写猜测结论。
- `下一步动作`：立刻执行的一步。
- `状态`：`进行中` / `待复测` / `已闭环` / `阻塞`。
- `是否需决策`：`是/否`；若是，写清需要用户拍板的点。

## 4. 同步节奏
- 高频短同步：每 15-20 分钟输出一次 1-2 句进展。
- 关键节点同步：出现“新阻塞、根因确认、修复完成”时立即同步。
- 避免长篇推理输出：只保留“事实 + 决策 + 下一步”。

## 5. 决策门禁（必须停下确认）
出现以下场景必须先确认，不直接执行：
- 即将修改业务代码或接口契约。
- 即将引入新依赖、外部服务或 MCP。
- 即将执行可能带来写操作或环境副作用的动作。

说明：若仅进行代码阅读、文档整理、只读排查，可直接继续。

## 6. 并行与优先级
- 默认限制在 `最多 3 个进行中问题`，其余进入待处理队列。
- 优先处理 P0（阻断联调主流程）问题，再处理 P1/P2。
- 若低优问题需要较长时间，先切出最小可验证路径，不阻塞主线。

## 7. 修复闭环标准
问题从“进行中”变为“已闭环”前，至少满足：
- 已给出修复动作或结论。
- 已完成对应验证（接口响应、页面行为、日志或测试）。
- 已说明残留风险（如“需前端复测”“依赖测试环境数据”）。

## 8. 交付输出模板（每轮/收尾）
每轮汇报建议固定为：
1. 当前进展：已完成/进行中事项。
2. 当前阻塞：阻塞原因与影响面。
3. 下一步：接下来 1-2 个动作。
4. 需你决策：仅列必须拍板项。

收尾时补充：
- 闭环清单：`已闭环` / `待复测` / `阻塞`。
- 风险清单：短期风险与建议跟进动作。

## 9. 与现有 skill 的关系
- 本 skill 是 `audit-project-workflow` 在“联调沟通效率”场景下的补充。
- 若涉及数据库写风险，建议叠加 `safe-sql-api-workflow`。
