# Safe SQL API Workflow

用于 `/Users/zyc/gxxm/audit` 项目在“补接口 + 连 SQL”场景下的安全执行规范。  
本 skill 只定义流程门禁，不直接授权写库。

## 1. 适用场景
- 新增/修改后端接口且可能触发数据库写操作。
- 需要直接执行 SQL（包括排查、联调、修数、DDL）。
- 联调过程需要证明“可回滚、可审计”。

## 2. 强制规则（硬门禁）

### 规则 A：默认只读
- 默认仅允许 `SELECT`、结构查看、Explain、只读联调。
- 未进入确认门禁前，禁止 `INSERT/UPDATE/DELETE/DDL`。

### 规则 B：写操作必须二次确认
- 涉及 `INSERT/UPDATE/DELETE/DDL` 时，至少两次确认：
  1. 方案确认：确认目标、条件、预计影响行、回滚方案。
  2. 执行确认：测试库验证通过后，生产执行前再次确认。

### 规则 C：先测试库验证，再生产执行
- 无测试库验证结果，不得进入生产写入。
- 测试库至少输出：
  - 命中行数；
  - 实际影响行数；
  - 回滚演练结果（或可执行回滚脚本验证）。

### 规则 D：关键写操作必须事务 + 回滚预案
- 关键写操作（批量更新、批量删除、核心表变更）必须明确事务边界。
- 必须提前提供回滚方案：
  - DML：反向 SQL 或基于备份恢复；
  - DDL：反向 DDL、快照或备份恢复路径。

### 规则 E：先 SELECT 验证命中范围，再执行写入
- 每条写 SQL 前必须有等价条件的 `SELECT` 预检：
  - 预估命中总数；
  - 样本主键（建议前 20 条）。
- 若命中范围与预期不一致，停止写入并回到方案确认。

### 规则 F：联调前后必须记录审计信息
- 联调前记录：
  - `request_params`
  - `expected_affected_rows`
  - `rollback_point`
- 联调后记录：
  - `response_summary`
  - `actual_affected_rows`
  - `rollback_executed`（是/否）

## 3. 标准执行流程
1. 需求分析：识别是否存在数据库写风险。
2. 只读排查：完成结构理解与 `SELECT` 命中预估。
3. 写入计划：形成“SQL + 影响范围 + 事务边界 + 回滚预案”。
4. 第一次确认：确认计划与影响范围。
5. 测试库执行：验证写入与回滚方案。
6. 第二次确认：生产执行前再次确认最终语句与影响范围。
7. 生产执行：严格按确认内容执行。
8. 联调归档：补齐前后审计记录。

## 4. 失败处理
- 任一门禁不满足：立即停止写入，回退到对应确认阶段。
- 回滚条件不清晰：禁止执行生产写入。
- 测试库不可用：禁止跳过测试直接生产执行。

## 5. Python 读取 Nacos（对齐 Java）约束
- Java（Spring Cloud Alibaba）通常由框架自动读取 Nacos 配置。
- Python 侧应采用显式 SDK 方式并与 Java 对齐同一配置命名：
  - 保持相同 `dataId/group/namespace`；
  - 启动时主动拉取配置；
  - 注册监听器处理配置变更；
  - Nacos 不可达时回退到本地兜底配置（`.env` 或本地文件）。
- 禁止在 Python 中写死与 Java 不一致的配置键命名。
