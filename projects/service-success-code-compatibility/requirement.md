# 需求文档

## 1. 背景
- 业务背景：测试环境可能对接不同后端或网关，成功响应码不一定固定为单一值。
- 当前现状：前端仅支持 `VITE_SERVICE_SUCCESS_CODE` 单值匹配，无法直接兼容多个成功码。
- 相关页面/模块：`frontend/src/service/request/index.ts` 请求成功判定逻辑，`frontend/.env.test` 环境变量配置。

## 2. 目标
- 核心目标：让 `VITE_SERVICE_SUCCESS_CODE` 在测试环境支持多情况配置（多值成功码）。
- 预期价值：减少联调时因响应码差异导致的误判失败，避免频繁改代码切换环境。

## 3. 范围
### 本次范围
- 支持 `VITE_SERVICE_SUCCESS_CODE` 通过逗号分隔配置多个成功码。
- 保持单值配置向后兼容。
- 更新 `.env.test` 示例配置与代码注释。

### 不在本次范围
- 不调整后端响应结构。
- 不改动 `demoRequest` 的成功判定逻辑。

## 4. 用户故事
- 作为联调开发者，我希望在 `.env.test` 一次性配置多个成功响应码，从而在不同测试后端之间切换时保持前端请求判定稳定。

## 5. 功能需求
- [x] `VITE_SERVICE_SUCCESS_CODE=0000` 仍按原逻辑生效。
- [x] `VITE_SERVICE_SUCCESS_CODE=0000,200` 时，任一匹配均判定为成功。
- [x] 允许配置值包含空格并自动忽略无效空项。

## 6. 非功能需求
- 性能：每次请求仅进行轻量字符串拆分与匹配，不引入可感知性能损耗。
- 安全性：仅本地配置解析，不新增安全面。
- 兼容性：兼容既有单值配置。
- 可维护性：实现放在请求层，逻辑清晰可读。

## 7. 数据与接口影响
- 前端影响：请求成功判定逻辑增强。
- 后端影响：无。
- 数据库影响：无。
- 第三方/MCP 影响：无。

## 8. 交互与界面说明
- 可抽离的组件机会：无（纯请求层逻辑）。
- 需要覆盖的状态：成功/失败判定路径。

## 9. 验收标准
- [ ] 单值成功码配置可正常请求成功。
- [ ] 多值成功码配置可命中任意一个成功码。
- [ ] 无效空白配置项不影响判定。

## 10. 风险与疑问
- 风险：若配置分隔符不统一（如使用 `|`），本次不会兼容。
- 疑问：是否需要未来扩展为支持 JSON 数组格式。

## 11. 确认关卡
- 用户已提出明确改动需求，按该目标实施并回报结果。
