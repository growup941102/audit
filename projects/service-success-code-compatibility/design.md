# 设计文档

## 1. 概述
- 对应需求文档：`projects/service-success-code-compatibility/requirement.md`
- 设计目标：在不破坏现有行为的前提下，为 `VITE_SERVICE_SUCCESS_CODE` 提供逗号分隔多值兼容。

## 2. 方案摘要
- 前端方案：将 `isBackendSuccess` 中的单值等于比较改为“解析后数组 includes”。
- 后端方案：无。
- 数据流转：`response.data.code -> String -> 与 env 解析后的成功码数组比对`。

## 3. 架构与模块拆分
### 前端
- 页面/容器：无。
- 可复用组件：无。
- Hooks / Services：仅调整 `request` service 的成功判定逻辑。

### 后端
- 无改动。

## 4. 文件规划
### 新增文件
- 无。

### 修改文件
- `frontend/src/service/request/index.ts`：支持多成功码判断。
- `frontend/.env.test`：将成功码改为多值示例配置。

## 5. 接口设计
- 接口地址：不变。
- 请求方法：不变。
- 请求参数：不变。
- 响应结构：不变。
- 异常处理：不变，仅成功判定条件增强。

## 6. 数据模型设计
- 无。

## 7. 状态与交互设计
- 初始状态：读取环境变量字符串。
- 用户操作：无界面操作。
- 边界场景：空格、空字符串、单值/多值混合。

## 8. 复用与封装设计
- 需要抽离的组件：无。
- 需要抽离的公共工具：本次可内联处理，保持最小改动。
- 为什么需要封装：当前改动范围小，过度抽象收益低。

## 9. 文档计划
- 需要补充的后端文档：无。
- 需要新增的功能文档：本目录三份文档。
- 面向前端同学的说明：在最终汇报中说明多值配置格式。

## 10. MCP 与外部依赖
- 是否需要 MCP：否。
- 使用目的：无。
- 预期输入/输出：无。

## 11. 测试方案
- 前端验证：以字符串样例验证 `0000`、`200`、`0000,200` 的匹配结果。
- 后端验证：无。
- 手工验证：联调接口返回不同成功码时观察是否进入成功分支。

## 12. 风险
- 技术风险：极低。
- 回滚/兜底方案：恢复为原单值比较逻辑。
